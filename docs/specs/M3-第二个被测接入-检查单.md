# M3 · 第二个真实被测接入 —— 检查单

> **用途**:M3 是"工具**通用性**"的验证(第一个被测是自用项目,不算通用性证据)。
> 本文件把**第一个被测接入时踩过的坑**固化成可照做的顺序 —— 以免第二家再接一遍。
> **前置**:业务方**选定被测方**(技术侧不自己找)。
> **纪律**:不改被测(除业务方授权);每步留下可复核的证据;结论只写能证伪的话。

## 0. 先要到的信息(向被测方)

| # | 要什么 | 为什么 |
|---|---|---|
| 1 | 仓库路径 / 版本(commit) | 报告要能锚定"测的是哪个版本";跨修复的基线**不可直接比较** |
| 2 | 接口与鉴权(端点、鉴权头、限流) | 适配器要用;限流会导致**假失败** |
| 3 | 数据源(知识库 / 向量库 / 语料位置)与**它自己的预期质量** | **本检查单第 2 步的核心输入** |
| 4 | 官方运行方式(compose / Dockerfile / 启动脚本) | ⚠️ **能走官方路径就走官方路径** —— 第一个被测的 harness 是"官方路径暂时不通"时的兜底,不是范式 |
| 5 | 是否暴露 `sources` / `citations` / `tool_calls` | 决定回放测试(T3)与来源类判据能不能做 |
| 6 | 它自己的评测集(若有) | 可作**交叉参照**,但**不直接当我们的评测集**(见 §2) |

## 1. 接口能否被适配(先做这个,再谈评测集)

对照 `app/eval_gate/adapters.py` 的适配器契约,逐项确认:

- [ ] 一个**问答**调用能拿到:**答案文本**(必需)、来源/引用(可选,决定 `sources` 类判据)、错误码语义
- [ ] **失败能与"答不出来"区分**:超时 / 4xx / 5xx / 配额 —— 分别映射到契约错误码(`E_SUT_*`),
      ⚠️ **配额耗尽必须与质量失败区分**(第一个被测就踩过:额度耗尽会被读成"质量崩了")
- [ ] **鉴权头名对得上**(第一个被测是 `X-API-Key`;写错会 401,而 401 很容易被误读成"被测差")
- [ ] `SUPPORTED_SUTS` 登记 + 契约(`contracts/评测-sut-adapter.md`)补条目
- [ ] **能力探针**:`/health` 返回 200 **不等于**答得了(第一个被测实测:健康检查过、却对真实问题一律回「无法回答」)

## 2. ⚠️ 语料核查(**本轮最贵的教训:先查语料,再定题**)

第一个被测上有**两次**教训、第二条规则(`DEC-007` / `DEC-010`):

> **评测集的期望必须能被"被测的数据源"支持 —— 否则你测的是"它会不会猜",不是"它答得对不对"。**

照做:

- [ ] 先**只读**遍历被测的数据源,确认**拟定的每一条期望都有出处**;
- [ ] 特别警惕**两种读法都讲得通**的问法(实测:`id=26`「文档中提到了几种数据库?」——
      "提到了"把任何提及都算进来,而只有一篇文档给出权威计数 ⇒ **同一份语料数 2 或数 3 都有理**);
- [ ] 警惕**需要跨文档推断**的问法(实测:`id=42`「用 Docker 部署 PostgreSQL 的好处」——
      语料只有"Docker 的通用好处"与"PostgreSQL 是什么",**没有二者结合** ⇒ 被测如实拒答反被判错);
- [ ] 拒答类用例要确认**语料里确实没有**(否则它考的是"该答不答");
- [ ] **不要把第一个被测的评测集直接套上去** —— 域不同,期望不成立

## 3. 评测集:先小后大

- [ ] 先做 **10–15 条冒烟集**(含:直答题 / 拒答题 / 1–2 条边界题),跑通链路;
- [ ] 冒烟集必须含**至少 1 条"该拒答"**与**至少 1 条"方向性/计数"**——这两类是判据最易出错的地方;
- [ ] 冒烟过了再扩全量;**每条 `source` 写清出处**(便于日后复核)

## 4. 运行与可比性

- [ ] 运行方式**固化进仓**(第一个被测的教训:脚手架散在 `/tmp`,重启丢过两次 → 已固化 `tools/sut-harness/`);
- [ ] **能力探针必须跑**,且它的结果进报告(否则"答不了"会被读成"质量崩")**;
- [ ] 记录**运行形态与生产形态的差异**,并写进报告的"可比性边界"一节
      (第一个被测的 harness 只挂 RAG 路由,中间件/缓存未加载 ⇒ 结论要连同这一点说明);
- [ ] 采集 **L1 真实基线**(延迟中位 / P95 / 错误率 / 墙钟 / judge 成本);
      ⚠️ 第一个被测实测:**墙钟距 180s 阈值仅剩 2–5% 余量** ⇒ 第二个被测**不要照抄这个阈值**,
      应按它自己的基线定,或改对**被测延迟**设阈值而非全链路墙钟

## 5. 出结论(这一步最容易说过头)

- [ ] 报告要能回答:**"这个被测能不能上线、依据是什么、置信边界在哪"** —— 这才是产品价值;
- [ ] 与第一个被测**不要直接横向比分数**:域、语料、judge 版本、用例集都不同 ⇒ 只能比**同口径的过程指标**
      (如 judge 成本 / 延迟 / 拒答正确率);
- [ ] **判分器一致性**:新被测若产生新的答案风格,应在**新条目**上再跑一次校准
      (`eval-gate calibrate`);⚠️ 旧的 `judge_refs.json` **样本已用尽**(一致率 1.00,无剩余分歧),
      且**缺"堆砌"条目**(DEC-009 §5)⇒ 新一批参照集要补这两类;
- [ ] 明确写清**这轮不能证明什么**(例如:n=1 的集成测试、单轮波动未做 A/B)。

## 6. 验收(M3 的完成判据)

- [ ] 第二家被测跑通一轮真实评测,产物齐(报告 + trace + 摘要);
- [ ] 结论可读(**门外人能据它做决定**),且**可比性边界**写明;
- [ ] 本仓**不因接入第二家而散架**:适配器走既有契约、评测集分域存放、无跨域硬编码(含绝对路径);
- [ ] 顺带验证**通用性假设**:至少记录一处"第一个被测独有的做法在这家**不适用**"的地方
      —— 那就是"这个门是通用的还是个例"的真实答案。
