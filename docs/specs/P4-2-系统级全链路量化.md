## 1. 背景与目标

B 步骤9 要求:模拟真实场景执行端到端测试 · 验证完整链路(任务规划 → 执行 → 记忆读写 → 工具调用 → 结果返回)·
监控**成功率 / 平均耗时 / P99 / 资源使用峰值** · 数据报告含环境/数据量/结果/对比基线 ·
产出《系统端到端测试报告》《性能基准数据》,并**产 L1(系统)与 L2(代理逻辑)基线供上线对比**。

现状缺口(实测,非推断):

- **L2 已有**(`eval/阈值.json: l2_task_completion.min = 0.80`),**L1 没有真实的**。
  `docs/reports/P4-1/性能基准数据.md` 自己写明:「要谈被测性能,必须读 `eval/runs/<run_id>.trace.jsonl` 的 span,
  **不能用本文件**」—— 因为那份文件的延迟**全部来自注入桩**(`inject_sut_ms`),不是被测性能。
- **T3 回放测试的前置不成立**(实测,见 §2 不做)。
- P4-1 的《端到端测试报告》已覆盖"门自身子进程级 + 真实被测一轮",且其依据已引用步骤9;
  本节点**不重做**它,只补**系统级量化**这一层。

**目标**:把"已有真实 trace"变成**机读的真实 L1 基线**,使"被测变慢了/错误率涨了"从"只能看日志"变成"可比对"。

**挂钩指标**(总纲 §4):本节点**产出 L1 基线**;L2 沿用既有 0.80;北极星(劣化被拦次数)不受本节点影响。

## 2. 范围

### 做

1. **T2 · 真实 L1 基线** —— 从**已有**真实 trace 提取:被测延迟分布(P50/P95/P99)、被测成功率、
   judge 延迟分布、整轮墙钟、吞吐(cases/s);按**被测(sut)**分组;落**机读**文件 `eval/l1_baseline.json`。
2. **可复跑的提取工具** —— `app/eval_gate/trace_stats.py`(纯函数)+ `tools/trace_stats.py`(CLI),
   分位数**复用** `app/eval_gate/bench.py::percentile`(最近秩法),保证与既有口径同源。
3. **《系统端到端测试报告》** —— `docs/reports/P4-2/`,含:真实链路量化结果、环境六要素、**局限声明**、
   T3 判定记录(附可复跑证据)、门禁四条逐条判定。
4. **《性能基准数据》的真实链路部分** —— `docs/reports/P4-2/性能基准数据-真实链路.md`;
   并在 P4-1 那份里加**一行回链**(只加指针,不改其历史结论)。
5. **门禁对照** —— B §四四条逐条判过/不过,结论走 `gate-review`(建议),**终裁 = 业务方签核**。

### 不做(明确排除)

- ❌ **不造 "live 压测模式"**(改 `tools/bench.py` 让压测走真实被测 + 并发)。
  业务方 **2026-09-13 定夺**;理由:对 v1 评测门而言,L1 的语义是"跑一轮多久 / 被测响应特性",
  不是服务 QPS;造并发压测属过度工程。
  ⇒ **本节点因此不产出"一天的业务流量模式"与"资源使用峰值"**(见 §3 假设 3、§11 已知缺口)。
- ❌ **不做 T3 回放测试** —— **前置实测不成立**:最近一轮真实 trace 里 `tool_calls` 出现 **0 次**;
  `app/eval_gate/adapters.py:61` 的 `SutOutput.tool_calls` 字段存在但**真实适配器从不填充**
  ⇒「理想工具序列」**无数据可对**。处置 = **记录判定 + 依据**(业务方 2026-09-13 定夺),**不改被测、不换被测**。

  > ### ⬆️ 2026-09-15 升格(收尾批次 **C2**):「当前不具备条件」→ **判「不适用」+ 触发条件**
  >
  > **为什么是升格而不是维持**:原措辞「**当前**不具备条件」暗示"再等等就有了"。
  > 但查过两家真实被测的形态后,这个暗示是**错的** ——
  >
  > | 被测 | 形态 | 有没有"工具调用"这回事 |

  > | `01.FastAPI RAG Agent` | RAG 问答,单轮检索-生成 | **没有** —— 端点是一次检索加一次生成,不存在工具序列 |

  > 「回放理想工具序列」这个动作**对 RAG 问答类形态不成立** —— 那就是**不适用**,不是**待办**。
  >
  > **触发条件(满足任一条即须重审本条)**:

  > 2. 任一在册被测**新增** `tool_calls` 字段并真实填充(届时 `adapters.py:61` 的字段才有数据可对);
  > 3. `expected.ideal_tool_seq` 被**实际写入**任何评测集条目(当前 4 套集里全为空)。
  >
  > **判「不适用」不等于删除**:字段(`adapters.py:61` / `schema.py:30`)与契约
  > (`contracts/评测-sut-adapter.md:21` / `评测-evals-schema.md:30`)**全部保留** ——
  > 它们是**触发条件 1/2 的接口**,删了就要重新设计。删的只是"它欠着账"这个状态。
  >
  > **本条不动任何代码,也不改任何被测**(沿用 2026-09-13 业务方定夺)。
- ❌ **不改阈值接线** —— L1 基线**只作记录与人工复核依据**,不接线为阻断项。

## 4. 组件与数据流

```
eval/runs/<run_id>.trace.jsonl        ← 已有真实产物(不改)
        │  obs.read_trace(path) -> list[Span]      (复用 app/eval_gate/obs.py:312)
        ▼
app/eval_gate/trace_stats.py          ← 新增:纯函数,无 I/O 副作用
  · span_groups(spans) -> dict[name, list[Span]]
  · latency_stats(spans, name, only_ok=True) -> dict   (复用 bench.summarize_latencies)
  · error_stats(spans, name) -> dict{n_ok, n_error, rate}
  · sut_of(span) -> str | None                         (attributes["sut"])
  · summarize_run(path) -> dict                        (一轮的 L1 记录)
  · merge_runs(records) -> dict                        (按 sut 聚合)
        ▼
tools/trace_stats.py  (CLI)           ← 新增:--runs / --glob / --out
        ▼
eval/l1_baseline.json                 ← 新增:机读 L1 基线
        ▼
docs/reports/P4-2/*.md                ← 人类可读报告 + 局限 + T3 判定
```

**最小链路片段(以真实一轮为例)**:
`evalset.load`(1)→ `run.evaluate`(1,根)→ `sut.call`(N)+ `rule.check`(N)+ `judge.grade`(N)→ `report.write`(1)。
L1 取 `sut.call` 的 `duration_ms` 与 `status`;墙钟取 `run.evaluate` 的 `duration_ms`。

## 6. 评估阈值与指标(变更即跑)

- **本节点不改** Prompt / 工具 Schema / 记忆策略 / 评估集 ⇒ **不触发 eval 回归**
  (门自身代码有改动 ⇒ 跑 `pytest`,覆盖率门在 CI 已硬门 85%)。
- **新增指标(L1,只记录不阻断)**:
  - `sut_latency_ms`:`sut.call`(status=ok)的 `{n,min,p50,p95,p99,max,mean}`
  - `sut_success_rate` = ok / (ok + error)
  - `judge_latency_ms`:`judge.grade` 的同一摘要
  - `wall_ms`:`run.evaluate` 的 `duration_ms`
  - `throughput_cases_per_s` = `cases / (wall_ms / 1000)`
- **L2**:沿用 `eval/阈值.json` 的 `l2_task_completion.min = 0.80`,**本节点不改**。
- 回归命令:`pytest -q`(全绿)+ `python tools/trace_stats.py --runs <id...> --out eval/l1_baseline.json`。

## 8. 失败处理与自愈

- **trace 文件缺失/空**:CLI 返回非 0 并打印期望路径(reference `_cmd_trace` 的处置),**不静默产出空基线**。
- **某 span 名一个都没有**(如 `judge.grade` 缺失):该项标 `n=0`,并在报告里**显式标注"未采集到"** ——
  不得用 0 冒充"很快"(沿用 `bench.percentile` 对空序列抛错的同一条精神)。
- **`percentage` 样本过少**(n<20):报告中保留但标注"高分位不稳健"(最近秩法在 n=3 时 p99 == max)。
- **降级链**:不适用(无外部依赖)。

### 已知缺口(明写在报告里,不装看不见)

1. **非并发、非"一天流量模式"、无资源使用峰值** —— §2 不做第 1 条的直接后果。
2. **样本为单轮**(每 sut 1–3 轮、每轮 4–48 条)⇒ 高分位不稳健。
3. **trace 无被测版本** ⇒ 跨轮可比性靠记账。
4. **T3 回放不具备条件** ⇒ "工具调用"这一环未被验证。
