## 1. 背景与目标

阶段3 已收口(PASS,D-11)。B 阶段4 是「上线前的质量防线」:先验证每个模块,再验证系统级完整链路,全部量化并出报告。

**形态适配(业务方 2026-09-11 定调)**:本产品是**评测门**(评测其它 Agent 的工具,D-5),B 阶段4 卡默认被测对象是"一个 Agent 系统"。故:

- **主(甲)**:把**评测门自身**当作被测系统 —— 单元/集成/压测/端到端/红队**都施加在 `app/eval_gate/` 与 CLI 上**;
- **辅(乙)**:用门对真实被测(`01.FastAPI RAG Agent`)做一次**可复现的端到端基准**(R1b 已跑通,本节点把它**固化为基准数据**)。

**挂的指标**:L1(系统)= 评测跑批延迟 / 错误率 / 成本(judge token);L2 = 任务完成率 / judge-人工一致率。基线已在 R2b 标定,本节点**补 L1 的系统级基线**。

## 2. 范围

### 做
- **单元/集成测试**:补**异常路径**覆盖(现 95 条偏正常路径);量**覆盖率**并设基线
- **压测**:量「**评测门自身开销**」与「**外部依赖(被测/judge)开销**」的分离 —— 这决定 L1 阈值该挂在哪
- **端到端(甲)**:门自身完整链路(装载 → 调被测 → 确定性 → judge → 聚合 → 报告 → exit)作为**可复现基准**
- **端到端(乙)**:真实被测一轮,固化为《性能基准数据》
- **红队(本仓附加)**:攻击"**门会不会被骗过**"(详见 §6)
- **产出 5 份报告**(B 要求),落 `docs/reports/P4-1/`

### 不做(明确排除)
- 不引入 **Locust**:门是**串行 CLI 批处理**,非 HTTP 并发服务;Locust 面向长驻服务,形态不符。改用 stdlib 并发跑批自证(零依赖)
- 不做**混沌注入**(网络分区/服务宕机)—— 属 B 阶段5(稳定性)门禁,本节点不越界
- 不改 `runner.py` 的**串行执行**语义(并发执行是 E5 后续项,需单独 DEC)

## 4. 组件与数据流

```
[eval 输入] → E1 装载校验 → E5 串行调度 ─┬→ E2 调被测(外部 HTTP/快照)
                                        ├→ E3 确定性规则(本地,~0ms)
                                        ├→ E4 judge(外部 LLM)
                                        └→ E6 聚合阈值 → E7 报告/exit
                        E9 观测:全程 span + 结构化日志(已具备)
```
**本节点新增**:① 覆盖率度量;② 压测跑批脚本(可配并发度,用于**分离自身开销 vs 外部开销**);③ 红队用例集;④ 报告生成。

## 6. 评估阈值与指标(变更即跑)

- **改动评估集**:新增「红队:攻击评测门自身」用例(见下),按「失败即补 case」入 `eval/cases/`
- **红队靶子(4 类,全部针对"门会不会被骗过")**:
  1. **作弊的被测**:被测识别出自己在被评测 → 输出讨好判分器的空话(门能否识破?`answer_contains` 硬门槛应能拦)
  2. **畸形输入**:被测返回超长/空/非 UTF-8/巨型 JSON → 门须记 fail 而非崩(R0 已部分覆盖,补测试)
  3. **judge 出参越界**:verdict 非法、score 超 [0,1]、超大 reasons → 门须 clamp/拒绝(E4 出参校验)
  4. **评测集投毒**:条目含畸形 expected / 恶意超长 input → schema 须**零模型调用即失败**
- **回归命令**:`pytest -q --cov=eval_gate --cov-report=term-missing`
- **L1 目标(本节点产出基线后回填)**:批处理吞吐 case/s、单 case P95/P99、门自身开销占比、错误率

## 7. 人在环中(HITL)
- 本节点**无**高影响/不可逆操作(纯本地测试与度量)。人机模式:**自动化**(结果由业务方评审)。

## 8. 失败处理与自愈
- 压测/端到端需**被测服务与网络**;不可用时:① 用**快照取法**(D-5)保证可复现;② 报告中标注"哪部分未跑、为什么"
- 外部依赖(judge/被测)抖动导致的失败 **不得计入门自身错误率** —— 与 §2 的"开销分离"同一原则

## 9. 观测点(观测左移)
- 复用 R3 的 `obs.py`(`run.evaluate` 根 span + 子 span);压测脚本**也必须接 trace**,否则无法分离开销
- 报告必带 `run_id` / `judge_usage`(成本),已在 R3/R2b 具备

## 10. 横切原则对照

- [ ] **安全合规**:红队 4 类即本节点的安全动作;报告不含被测原文(沿用 R3 脱敏口径)
- [ ] **成本与 ROI**:压测会真实消耗 judge token → **压测轮次与规模须先报备**(预算),不得无上限跑
- [ ] **多 Agent 协作**:不适用(本节点无多 Agent 交互)
- [ ] **信任进化与隔离**:基准数据供后续对比(= 防劣化的锚点)
