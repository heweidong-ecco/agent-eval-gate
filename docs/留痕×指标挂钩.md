# 留痕 × 指标挂钩 · git/GitHub ↔ L1/L2/L3

> **用途**:把"上线指标验收"落到 git/GitHub 留痕链上——issue 有模块标签,PR 有评估证据,CI 有 eval-gate,release 带《L1/L2/L3 对比表》,监控事件回写 issue 后复盘。让每个版本都能回答:"这版比上版,指标变好了还是变差了,凭什么?"(依据 `02-增删映射表.md` §4-4;B `06-优化-版本迭代与发布策略-v1.0.md` "每版本绑定评估报告与发布记录"。)
>
> **三层指标定义**(详细口径见 B `02-执行方法论/02-方法论-分层指标体系-v1.0.md`、`05-模块-监控告警与仪表盘`):
> - **L1 系统**:延迟 P50/P95/P99、QPS、错误率、资源、Token/成本。
> - **L2 代理逻辑**:任务完成率、工具调用准确率、自愈触发率、平均步数。
> - **L3 业务**:人工介入率、CSAT、处理时间缩短%、FTE 节省。
> - 北极星 = 统领 L1/L2/L3 的业务指标(B `agent-system-creator/SKILL.md` 步骤 12)。

## 一、留痕链总览

| 留痕件 | 何时 | 挂的 B 概念 | 必须含的证据 / 内容 |
|---|---|---|---|
| **Issue** | 想法立项/发现问题 | B 14 模块(见 `github/issue-模板-labels.md`) | label = 改动模块 + `eval`/`prompt`(是否跑评估/是否改提示词)+ 优先级;验收口径写清 |
| **Branch** | 开工 | `github/分支-commit-规范.md` | `feat/<issue#>-<slug>`,一条分支一个 issue |
| **Commit** | 每步 | Conventional Commits + **提示即代码/评估集同库版本化**(B `03-原则-信任进化与隔离` §一、`06-优化-版本迭代` §2.1) | 引 issue 号;Prompt/评估集/代码一起入库可回滚 |
| **PR** | 合并前 | B `02-方法论-工程纪律与CI-CD` §一(契约测试)、`05-模块-评估与测试` | **必附**:① 评估集回归结果(命令+通过率+阈值对比)② 是否改 Prompt/工具/记忆策略(改了什么)③ 观测证据(trace_id/日志/截图)④ 契约漂移说明(见 `github/pr-模板-评审.md`) |
| **CI** | PR / push | B `02-方法论-工程纪律与CI-CD` §4.1 + 发布数据门 | 代码门(lint/test/build)+ **eval-gate**(变更即跑评估集,低于阈值红;见 `github/ci-cd-骨架/ci.yml`) |
| **Merge** | 通过后 | — | squash/merge + 删分支 |
| **Release** | 上线点 | B `06-优化-版本迭代` §2.1"每版本绑定评估报告与发布记录" | tag `vX.Y.Z` + 必附《L1/L2/L3 对比表》(模板见下)+ 发布记录 |
| **监控事件** | 运行期 | B `05-模块-监控告警与仪表盘`(三层联动预警)、`04-阶段6`(持续改进闭环) | 告警/异常 → **回写关联 issue(#)** → 进复盘 |
| **复盘** | 周/迭代 | B `04-阶段6` 步骤 12、`06-优化-*` | 沉淀行动项 → 新 issue(owner=你 + 截止) |

## 二、Release 必附《L1/L2/L3 对比表》模板

> 每发一个版本(尤其动 Prompt/模型/记忆/工具的版本),把下表贴进 Release notes / PR body。基线来源:B 阶段四产 L1/L2 基线、阶段一痛点基线产 L3 基线(`02-方法论-分层指标体系`);灰度对比见 `06-优化-版本迭代` §2.3。

```markdown
## 版本 <vX.Y.Z> L1/L2/L3 对比

| 层 | 指标 | 上一版基线 | 本版(灰度/全量) | 判定(↑/↓/≈) | 阈值/门禁 |
|---|---|---|---|---|---|
| L1 系统 | P95 延迟 / QPS / 错误率 / Token成本 | | | | 阶段四压测基线 |
| L2 代理 | 任务完成率 / 工具准确率 / 自愈触发率 / 平均步数 | | | | 评估集回归阈值(低则阻断) |
| L3 业务 | 人工介入率 / CSAT / 处理时间缩短% / FTE | | | | 阶段一痛点基线 |
| 北极星 | <自动解决率等> | | | | 统领口径 |

观测证据:评估集版本号;trace 链接/采样;灰度流量比例与结论时长;回滚预案是否触发。
```

## 三、CI 是两套门,别合并成一个绿灯

- **代码门**(lint/test/build):通用工程壳,保证"代码能跑、不崩"(B 未覆盖)。
- **评估门(eval-gate)**:Agent 核心门——变更即跑评估集、低于阈值**自动阻断**(B `02-方法论-工程纪律与CI-CD` §4.1、`05-模块-评估与测试` §四)。
- 两套都必须**可独立看结果**(别混成一个绿灯),避免"代码绿但行为劣化"漏上(引 `02-增删映射表.md` §6-6)。

## 四、与指标基线的联动纪律

1. **版本可比**:指标带版本号,支撑灰度对比与回归判断(`05-模块-监控告警` §四)。
2. **回归自动化**:评估流水线进 CI,变更即触发(`05-模块-评估与测试` §五)。
3. **失败即补 case**:线上新失败 → 立即补进评估集复现(`05-模块-评估与测试` §10.3 纪律 4)。
4. **监控事件回写**:任何监控告警(尤其 L1 劣化预警 L2→L3)要能定位到 issue/版本;复盘时回链到《L1/L2/L3 对比表》。
