## 4. 瓶颈分析与结论

1. **门自身不是瓶颈**:0.051 ms/case 的编排开销,相对任何真实 LLM 调用(百毫秒级)可忽略。
2. **并发策略必须按依赖类型选**:
   - 纯离线(快照/桩,CPU-bound)→ 并发**有害**(线程调度 + GIL),**保持 K=1**;
   - 真实被测/judge(IO-bound)→ 并发**近线性**,可按需开 K;
   - 这与"一律加并发"的直觉相反,是本节点实测得到的主要工程结论。
3. **`runner` 的串行语义不改**:上表的并发是**多个独立 `evaluate()` 进程内线程**实现的
   (每个 run 各自完整、互不共享状态),`runner.py` 内部的逐 case 串行语义未动(那是契约)。

## 5. 局限(必须一起读)

- **延迟来自桩**:`--inject-sut-ms` 是**注入**的休眠,不是被测真实性能。
  本文件的用途是**验证开销分离方法 + 给出门自身开销量级**,不是给被测定性能基线。
- **真实链路的延迟/P95/P99 本轮未取**(真实被测无作答能力,见《端到端测试报告》§3)。
  将来取数应直接读 `eval/runs/<run_id>.trace.jsonl` 的 span(**不要**为此改桩语义)。
- **CPU/内存占用未采**:本节点用 `env_fingerprint()` 记了环境(`macOS-13.6-x86_64 / python 3.11.16 / 4 核`),
  但未做资源曲线;B 卡的「资源:CPU/内存/GPU」一条**未达标**,列入后续(`P4-2` 或阶段5)。
- **未用 Locust**:形态不符(门是串行 CLI 批处理,不是长驻 HTTP 服务),理由与代价见 `DEC-003`。
