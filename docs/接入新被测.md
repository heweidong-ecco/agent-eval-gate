# 接入一家新被测(要动什么 · 不要动什么)

> **这份文档回答一个问题**:**别的团队拿这个门去测他们自己的系统,需要改我们的源码吗?**
> 答:**要,但只有 3 处,且全在适配器层**;其余全是加数据。
> 依据 = 代码事实(每条给 `文件:行号`)+ 两次真实接入的实测(见 §6)。
> 相关:`docs/specs/M3-第二个被测接入-检查单.md`(选型与流程)· `contracts/评测-sut-adapter.md`(接口契约)

---

## 0. 先判"够不够格"(硬门槛,不做的话后面全是白工)

一句话判据:**它能不能对一个问题,给出一段"可以被判对错的文字"?**

| # | 门槛 | 为什么硬 |
|---|---|---|
| 1 | **输出文本答案**(给输入 → 拿回一段自然语言) | 这是已签核的 **C1/D-5 架构定位**:本门判「输入 → **输出文本答案**(含引用/证据)」。三层判据(`answer_contains` / `must_refuse` / `answer_not_contains`)**全建立在文本上** |
| 2 | **可被程序调用**(HTTP / CLI / SDK)+ 鉴权可控 | 手动点的系统进不了 CI |
| 3 | **能区分"答不出来"与"系统故障"**(超时 / 4xx / 5xx / 配额) | 混在一起会**冤枉被测**(实测踩过:配额耗尽被读成"质量崩了") |
| 4 | **有受控数据源 / 明确知识边界** | 期望必须有出处;没有受控语料的通用助手只能测格式与拒答 |
| 5 | **业务方授权**(只读接入、跑评测、结论进报告) | 结论要对外 |
| 6 | 限流可预期 | 限流制造**假失败** |

完整版(含加分项:形态越不同越值钱、是否暴露 `sources`/`tool_calls`、官方运行方式等)见 `docs/specs/M3-第二个被测接入-检查单.md` §0。

## 1. 必须改的代码:**3 处**(全在 E2 适配器层)

> **判定内核不动**:`runner.py` / `rules.py` / `judge.py` / `report.py` / `cli.py` 里
> **没有任何被测名字的分支**(`grep` 命中数为 0)。被测相关的硬编码**全部集中**在 `adapters.py`。

| # | 动作 | 位置 | 性质 |
|---|---|---|---|
| **1** | 写一个 `SutAdapter` 子类:`id` + **怎么组请求** + **响应怎么映射成 `SutOutput`** | 基类 `app/eval_gate/adapters.py`(约 74-80 行);三个现成范例:fastapi-rag / toolkit-prototype(含两形态子类)/ mini-rag-qa | 新增代码(~100 行) |
| **2** | 注册:`register_adapter(id, 工厂)` | `app/eval_gate/adapters.py` 文件末尾的注册区(现有 4 行) | 新增代码(1 行) |
| **3** | 把 id 加进 `SUPPORTED_SUTS` 白名单 | `app/eval_gate/schema.py`(顶部常量) | 新增代码(1 行) |

⚠️ **2 与 3 是两处独立代码,值必须一致**:

- 只注册不加白名单 → 评测集装载即失败(`E_UNKNOWN_SUT`);
- 只加白名单不注册 → 跑到该 case 时 `KeyError`(适配器未注册)。

⚠️ **接口约束**:核心管线调适配器时**无条件传 `quality=`**(`runner.py` 的 `_grade_case`)。
新适配器工厂**必须能接收这个关键字**(不需要就"接收并忽略",现有实现都这么做,源码里有注释说明),否则 TypeError。

另需同步(非代码或轻量代码):
- 契约里的 sut 枚举与适配器映射段:`contracts/评测-evals-schema.md` · `contracts/评测-sut-adapter.md`;
- 断言 id 集合的测试:`tests/test_schema.py` · `tests/test_adapters.py`。

## 2. 只需加数据(不改代码)

| 要加的 | 说明 |
|---|---|
| **评测集**(一个 JSON) | 顶层 `version / threshold_ref / sut_default` + `evals[]`;**文件名与路径没有任何代码注册过** —— CLI 由 `--evals <path>` 显式传入,运行时按 `case.sut` 派发 |
| **被测的连接配置** | 新适配器自己的环境变量(如 `EVAL_SUT_<X>_BASE_URL`),写在适配器类里;`.env.example` 补示例 |
| **语料**(若被测需要) | 视被测而定:有的要评测方塞(第二家提供 `POST /retrieval/index`),有的要评测方 seed(第一家要在它 DB 里灌 golden 文档) |

⚠️ **每条 case 必须有非空 `input.question`(字符串)** —— 这是 schema 的硬约束。
非问答形态(如结构化抽取)把输入文本塞进 `question` 复用该字段(见 `eval/toolkit_extract_smoke.evals.json`)。

## 3. 形态怎么建模(`sut` 的真实语义)

> **`sut` = 「适配器配置 id」,不是「被测系统」。**

- **一家被测可以有多个 `sut`**:同一服务、不同形态各占一个 id
  (实测:`ai-field-delivery-toolkit` → `toolkit-qa` / `toolkit-extract`,同一入口、`template` 不同);
- `registry` 键 · `SUPPORTED_SUTS` 成员 · `Case.sut` 取值 = **同一个命名空间**;
- ⇒ **"适配了几家被测" ≠ "注册了几个 sut id"**。

**为什么要按配置分 id**:不同形态的**参数集可能不同**,硬塞进一个适配器会写出内部 if/else 分支。
实测第一种情况:第二家的抽取形态**不接受 `kb_run_id`**(带上会 500)⇒ 用 `sends_kb` 类属性分开表达,
比在 `run_case` 里写 `if template == ...` 更清楚。

## 4. ⚠️ 现状的两处结构限制(真"给别人用"时会挡路)

| # | 限制 | 现状 | 影响 |
|---|---|---|---|
| **1** | **阈值不能按被测分档** | `runner.py` 的 `THRESHOLD_FILE` 是**单一常量**,只认三个固定键(`l2_task_completion` / `redteam_zero` / `judge_human_agreement`);`--threshold` 只是**覆盖同一份**数值 | 不同被测需要不同基线(实测:第一家墙钟 172s、第二家 21.8s ⇒ **同一个 180s 阈值对第二家毫无意义**)。要 per-SUT **必须改代码** |
| **2** | **判据表达力偏弱** | 软层是「`answer_contains` 含其一即符」+ 硬层禁现/必拒 | 对**结构化抽取**这类任务,抽对 1 个即算过 ⇒ 只能靠 `answer_not_contains`(硬层)间接测"不臆造"。要正式判抽取质量,需要"**必须包含全部 N 项**"的判据(判据扩展,须 DEC) |

另:报告的 `sut_versions` 字段在契约里有、代码里**尚未写出**。

## 5. 接入的验收(照做即可)

1. **离线彩排**(零 judge token,但对真实服务发请求):`--offline` 跑一遍 ⇒ 验链路与出参归一化;
2. **真实一轮**:用真 judge 跑,核对三件事 —— ① `生效 judge 配置`(`max_tokens` 是 DEC-006 后的 4096);
   ② `judge 记账: 调用 N / 用例 M`(**N−M = 被重试掩盖的失败次数**);③ trace 里 `judge.grade` span 的
   `(attempts, finish_reasons)` 是否全是 `(1, 'stop')`;
3. **出报告**:`docs/reports/<里程碑>/`;⚠️ 必须写明**"这轮不能证明什么"**(语料是否合成 / n 多大 /
   单轮还是多轮 / 阈值是否按本家标定 / **不与其它被测比分数**)。范例:`docs/reports/M3/第二个被测评测报告.md` §5。

## 6. 两次真实接入的实测结论(可直接复用)

| # | 发现 | 来源 |
|---|---|---|
| 1 | **被测内部故障 ≠ 答得不好**:被测把「LLM 调用失败」当答案返回(HTTP 仍 200)⇒ 适配器**必须**映射为 `E_SUT_5XX` | 第二家 |
| 2 | **别传被测的内部治理参数**:第二家的 `project_id` 会触发它自己的「数据未达标不进原型」门禁(403),那是它的治理 | 第二家 |
| 3 | **能走官方路径就走官方路径**:第二家的 `docker-compose` 是给基础设施的,而它的向量库是**嵌入式**(零外部服务)⇒ 本地 venv 直跑即可 | 第二家 |
| 4 | **拒答话术每家不同** ⇒ 拒答判据是**词表 + 正则**,新话术有漏判风险(已知脆弱点) | 第二家(实测触发) |
| 5 | **替身必须与生产路径同判**:离线 `FakeJudge` 曾与硬层用**两套**拒答词表 ⇒ 离线结论不代表线上(已修,判定收敛到 `rules.is_refusal`) | 本仓自身缺陷 |
