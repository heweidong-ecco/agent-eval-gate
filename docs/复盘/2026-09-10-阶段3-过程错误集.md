## 二、教训(下次可照做的规则)

1. **凡「已签核物」(契约/评测集/阈值/签核记录),落码或改码后必须逐条对账**:枚举值、字段名、形参签名、**实际生效值**。本阶段 5 处漂移全靠这条才抓出来。
   → 可操作化:CI 加「**契约↔实现对账**」检查(见行动项 3)。

2. **文档写了 ≠ 生效了。** 「已标定/已定义」的产物必须**实测一次生效路径**(A5 就是没测才差点放过)。
   → 可操作化:凡新增/修改签核物,**验收里必须有一条「证明它真的被读到」的测试**。

3. **兜底 `except Exception` 会把真凶藏成受害者。** A4 让评测门自己的 bug 表现为「被测调用失败」。
   → 可操作化:catch-all 分支**必须保留原始异常类型/消息**且**不得覆盖可区分的错误码**。

4. **纪律靠"记得",结构靠"躲不掉"。** 本阶段实证:同一 Kit 里,**有 hook 的纪律(Kit 缺陷反馈)每轮都执行了;只有文字的纪律(失败即补 case)零执行**。
   → 可操作化:任何新纪律,**至少落两处**:① 每会话必读的锚点(`CLAUDE.md`)+ ② 一处硬约束(hook 或 CI)。

5. **推荐前先查事实源。** 通用 Kit 门禁 ≠ 本项目已签核约定(D1 两次翻车)。

## 四、对母体 Kit 的反馈

**KD-7 候选**(已提请登记,证据 1/2,留观察态):

- **线索**:K5 适配断层 / 纪律落地机制缺失
- **证据**:① 全库唯一 hook 是 `kit-sentinel.sh`,只服务「母体 Kit 缺陷反馈」;② `eval/cases/`、`飞轮/{反馈,案例库,提炼,上线}/`、`docs/复盘/` 三处目录**只写在 README 一句话里,scaffold 一律不创建、无模板、无示例**;③ 全库 grep `错误集`/`postmortem`/`incidents`/`bad_cases` **命中 0**;④ **实证**:agent-eval-gate 跑完整整一个阶段3,`eval/cases/` 从未存在,「失败即补 case」**零执行** —— 而同一 Kit 里有 hook 的「Kit 缺陷反馈」**每轮都执行了**
- **影响**:Kit 用**文字**承载纪律,却无**结构性落地**。派生项目会**系统性地漏执行**这类纪律,且漏了不会有任何提示
- **最小修复建议**:① scaffold 随包创建上述目录 + 各放一份最小 README/模板;② 把「失败即补 case」写进 scaffold `CLAUDE.md` 的纪律段(而非只写在 `eval/README.md`);③ 提供 opt-in 的 Stop hook 模板(与 `kit-sentinel` 同风格);④ CI 骨架加「改动评测集未补 case → 失败」检查
