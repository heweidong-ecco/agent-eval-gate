## 1. 问题(实测,非推断)

### 1.1 名实不符(实锤)

`app/eval_gate/rules.py:63` 的注释自己写着:

> `hits`:报告用文案(**硬层失败原因 + 软层未命中提示**)

实际装的内容(`rules.py:103/109/116/121`):

| 内容 | 是什么 |
|---|---|
| `"被测无输出"` | 硬层失败原因 |
| `"应拒答却输出了实质内容/未见拒答表述"` | 硬层失败原因 |
| `"命中禁现词: 'X'"` | 命中了**禁现**词(仍是问题) |
| `"未命中任一期望关键点(软层,交判分器定夺): [...]"` | 未命中期望(仍是问题) |

⇒ **装的全是「问题」,字段名却叫 `hits`(命中)**。且其中一条的**文字**里还带「命中」、另一条带「未命中」,
⇒ 单看名字**无法推断方向**。

> 📌 更正一处我自己的初判:我先说它"装两种相反语义"——**读快了**。
> 严格看语义是**统一的(问题清单)**,错的是**名字**。

### 1.2 更本质:确定性层的结论被喂给了判分器

`runner.py:219` 构造 judge 输入时传 `deterministic={"passed": rule.passed, "hits": rule.hits}`,
`judge.py:234` 把它**原样 JSON 化**塞进 user message —— 而 **system prompt 里没有任何一句解释这个字段**。

**为什么这是问题**(三条,均有代码依据):

1. **硬层结论对 judge 毫无用处**:`runner.py:227` —— 硬层不过时 `res["verdict"]` **直接判 fail**,
   **judge 的意见被覆盖**。⇒ 告诉它硬层结论**不影响结果**。
2. **会锚定**:judge 看到 `{"passed": false, "hits": ["未命中…"]}` ⇒ 被**引导**向"这条有问题",
   而 `DEC-004` 的设计恰恰是**软层由 judge 独立判断**(硬层权威、软层 judge 权威)。
3. **字段未解释 + 名字错**:未解释的字段本就该最小化;这个名字还反向。

## 3. 建议

**分两步,先 A 后 B**(待签核):

1. **A 现在做**:零 token、零行为变化,消除名实不符 —— 这是**纯收益**;
2. **B 单独立项**:它改的是**判分器输入** ⇒ 按本项目纪律(改 Prompt/判据 ⇒ 必跑 eval 回归)
   **必须先有回归证据**,故须**先报备约 3 万 token**。

**为什么不直接 C**:B 没有证据前做了就是**赌** —— 去掉一个字段可能让 judge 变好、也可能变差;
本项目已有先例(**DEC-006**:判分器问题**两次归错因**),教训是**先取证再动**。

**为什么不选 D**:它默认接受"代码里的名字与内容相反"。本项目一贯立场是**结构 > 提醒**。
