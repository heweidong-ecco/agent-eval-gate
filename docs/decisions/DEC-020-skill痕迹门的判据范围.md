# DEC-020 · 门 2(skill 痕迹门)的判据取了「会话累计」,不是「本次改动前」

- 日期:2026-09-16 · 状态:**✅ 已签核**(业务方 2026-09-24;签核号 **D-29** —— 采纳 **α**)
- 上游:`CLAUDE.md` 纪律表(**命中即必须调用**)· `A2-R5`(「加硬门,并**逐条如实标注强度**」)
  · `A2-R10`(「能自动采集既有机器痕迹的,就不要靠自述」)
- 触发:2026-09-15 会话末,业务方追问「**哪些之前用的 skills 现在跳过了**、留痕-check 用了吗」
  ⇒ 查 `.claude/traces/latest.json` 得到客观数字,**与锚点里"命中即必须调用"的承诺不符**
- 预算:**零 token**(本 DEC 只是诊断 + 方案;实施若动 hook,**须配测试**)

## 1. 事实(客观采集,非自述)

2026-09-15 那场会话结束时,`.claude/traces/latest.json`:

```
skill_calls = 4    test-driven-development(1) · using-git-worktrees(1)
                   using-superpowers(1) · 留痕-checks(1)
bash_calls  = 208 · edit_calls = 38
```

| skill | 锚点要求的触发 | 会话内实际 |
|---|---|---|
| `test-driven-development` | **写或改实现代码** | **1 次**(会话早期)。之后 4 个编码任务(含**改判分器输入**的 A2)**一次没调** |
| `留痕-checks` | **每次 commit / PR 前** | **1 次**。之后 **5 个提交 + 3 个 PR** 没调 |
| `verification-before-completion` | 声称"完成/通过" | **0 次**(而该会话做了**大量**完成声明) |
| `systematic-debugging` | 遇 bug / 测试失败 | **0 次**(实际修了 CI 红 / JSON 污染 / 语法错 / 清单写坏) |
| `requesting-code-review` | 请人评审 | **0 次**(开了 4 个 PR) |
| `executing-plans` | 写/执行实施计划 | **0 次** —— ⚠️ 而对话里写过「**Using `executing-plans` 的框架推进**」 |

> ⚠️ 最后一行比"漏用"更坏:**没调用就 announce**,是把"记得那个 skill 大意"
> 冒充成"按它做了"。`using-superpowers` 明写 announce 的前提是**真的调用**。

**而这期间门 2 <u>一次都没有响过</u>。**

## 2. 根因:判据是**会话累计**字段

`.githooks/commit-msg` 的门 2 读 `.claude/traces/latest.json` 的 `skills`,判断
**本会话里有没有出现过** `test-driven-development` —— 而 `skills` 是**会话累计**的。

> ### ⇒ **第一次调用之后,门 2 对本会话剩下的<u>所有</u>提交永久满足。**

会话开头调一次 TDD,之后改 10 个文件都不再有任何结构压力。
**门 2 从"那次调用"起,就变成了一个<u>永远不失败</u>的检查。**

## 3. 为什么这条值得单独立 DEC(而不是当"小 bug"改掉)

### 3.1 它命中的是本仓/KB 反复列出的**典型形状**

`A2-R5` 要求「加硬门,并**逐条如实标注强度**」。而门 2 现在被标为 **硬**。
实际上它是:**一旦满足就永久满足** —— 即
**"验证动作永远不失败"**。这正是 KB `A5`(验证的假象)与 `A2` 篇反复列的形状。

**一个永远不失败的检查,和没有检查是同一件事** —— 而它比没有检查更坏:
**它会让下游(锚点/复盘/签核)相信"纪律有结构兜着"。**

### 3.2 KB 自己的强度表里,**已经写着这个洞**

`A2-R5` 的强度表原文:

> 「skill 痕迹门 | 改了实现代码,但**本会话** transcript 里没有该调用的 skill → 拒绝提交 | **硬**」

**「本会话」这个词就是洞本身。** ⇒ 这不是本仓的实现跑偏,
而是**规则文本**与**实现**共享了同一个隐含假设。⇒ 修**两边**。

### 3.3 它与 `DEC-019` 是**同族**

`DEC-019`(同批产出):判分器提示词用**字符串检查**代替**语义检查**;
本条的候选守卫(`tests/test_judge_budget_truncation.py:229`)同样是**字符串检查**。

⇒ 三条同族:**判据取了"看起来对"的东西**(会话累计 / 字符串 / 表面命中)。
这正是本仓 `docs/复盘/2026-09-13-判据依赖了不该依赖的东西.md` 的那一族。

## 4. 备选方案

| 方案 | 内容 | 代价 / 风险 |
|---|---|---|
| **α. 判据改成「本次改动之前」**(推荐) | 记录**事件序列**(而非累计计数),hook 比较「最后一次 `test-driven-development` 调用」与「本次提交里第一个实现改动的时刻」;前者须**不早于**后者所属的连续工作段 | 需扩 `skill-trace.sh` 的输出(加**有序**事件);**可能误拦**(沿用上一次调用做同一件事的合法情形)—— 必须配**豁免**与**测试** |
| **β. 改成「最近 N 次改动内」** | 粗粒度版:只要最近 N 个提交内有 TDD 调用即可 | 实现简单;但**N 取多少都是拍的**,且同样能被"顺手调一次"绕过 |
| **γ. 维持判据,但如实降级强度标注** | 把门 2 在锚点与 KB 里的强度从「硬」改成「**软(一次调用后永久满足)**」 | 零实现成本;符合 `A2-R5` 的「**如实标注强度**」—— **不做假承诺**;但纪律仍会掉 |
| **δ. 两者都做** | 先 γ(立刻不说谎),再 α(真修) | 推荐路径 |

## 5. 推荐:**δ —— 先如实标,再真修**

**理由**:`A2-R5` 的原话是「加硬门,并**逐条如实标注强度**」——
**顺序上,诚实标强度优先于把门做硬**。现在的问题是**门被标成硬的、实际是软的**,
这与"没有门"相比,**多付了一份"以为有兜底"的代价**。

⇒ 分两步:
1. **γ(零成本,先做)**:锚点 + KB `A2-R5` 的强度表里,把这个门标成
   「**硬,但判据是会话级 ⇒ 一次调用后对本会话永久满足**」;
2. **α(须配测试)**:把判据改成"本次改动之前",并**先写测试证明它<u>能红</u>**
   (本仓对守卫的一贯要求:突变验证)。

## 6. ⚠️ 认下的边界(不得读成"纪律没用了")

- 本 DEC **只诊断门 2**;它**不主张**"锚点对应表"等**软层**没用 ——
  `A2-R5` 的立场是**软硬并存,各自如实标注**;
- **α 有误拦风险**:同一件工作在多次提交里推进时,"本次改动前"可能落在上一次调用之前。
  ⇒ α 必须带**显式豁免**(同 `[no-test: <理由>]` 的既有约定),且**豁免率可统计**;
- **本 DEC 不改变**任何"该调用哪个 skill"的表(那是 `CLAUDE.md` 纪律表的事)。

## 8. 实施记录(2026-09-24 · **#79**)

**落地判据**(第三版;**前两版都被实跑证伪**):

> 取 `lo` = **上一次 `git commit`** 的时刻(转录里它是 Bash 调用);
> **通过 ⟺ 存在一次 `test-driven-development` 调用,时刻落在 `(lo, 本次最早那次实现编辑]`**。
> 人话:**自上次提交以来、动手之前,调过 TDD。**

**三版的过程(值得留)**:

| 版本 | 锚 | 结局 |

### 8.1 ⚠️ 强度**如实更正**(`A2-R5` 要求)

- ✅ **它现在<u>会失败</u>了** —— 不再是"一次满足后永久满足";
- ⚠️ **但仍不是纯硬**:有一条 **`undecidable` 通道** —— 本会话在上次提交后**未编辑过这些文件**时
  **不阻断**(误拦是守卫被关掉的头号原因)。**代价(认下)**:该路径**可被利用**,
  故它**每次都会出声**,不当成"通过"。
- ⇒ **如实强度:「硬,判据=时序;另有一条"判不了"的不阻断通道」**。
