## 1. 问题:两条独立的问题被同一个现象暴露

**现象**:真实链路 5 轮跑完后,发现**在案的 L1 阈值已被观测越线**,而且**越线不会有任何东西变红**。

**在案阈值**(`总纲.md` §4 与 `eval/阈值.md:25-30`,同一套值):

| L1 阈值 | 文档记的"实测" | 本轮真实观测(48 条) | 判定 |
|---|---|---|---|
| 单轮评测墙钟 **< 180 s**(**40 条**) | 86.9 s | 171.7 / 176.3 / **269.2 s** | ❌ **一轮越线**;另两轮仅 2–5% 余量 |
| `sut.call` 中位 **< 3 s** | 916 ms | 1594 / 1673 / **3537 ms** | ❌ **一轮越线**(池化 p50 2364 ms 未越线) |
| `judge.grade` 中位 **< 5 s** | 1247 ms | 1583 / 1637 / 1630 ms | ✅ |
| 错误率 **< 1 %** | 0 | 0 % | ✅(⚠️ 口径另有歧义,见 §2.3) |
| 埋点开销占比 **< 5 %** | 沿用 B 参考 | 门自身编排 ≈ **0 s** | ✅ |
| judge Token / 成本(40 条一轮) | 16,919 tokens | 28,561 / 28,880 / 29,905(48 条) | 口径过时(**非阈值**,是记录项) |

**三条彼此独立的问题**(混在一起谈会得出错的结论,故分开):

- **2.1 口径过时**:阈值按 **40 条**时代标定,评测集现为 **48 条**(+20%);且"实测"是**单点**(R1b 一轮)。
- **2.2 从未接线**:`eval/阈值.json` 的机读键只有 `l2_task_completion` / `redteam_zero` / `judge_human_agreement`,
  **没有任何 L1 键** ⇒ `runner.load_thresholds()` 不读它 ⇒ **L1 越线在 CI 里是静默的**。
  > 这与本项目此前修过的「阈值未接线」(`R2b 遗留①`)是**同一形状**;与避坑库 `A5`(验证的假象)/`A4`(门会腐烂)同族。
- **2.3 错误率口径有歧义**(接线前必须先澄清):`eval/阈值.md:28` 自己写着
  「R1b 实测 0(**4 个 error span 均为「该 case 判 fail」的预期标记**)」——
  如果 `span.status=error` 同时被用来表示"该 case 质量判 fail",那它**不是系统错误率**,接线会把"评测集里有用例失败"误报成"系统出错"。

## 2. 为什么"不能直接把阈值调大"

**关键事实(本轮实测,不是推断)**:墙钟与 `sut.call` 延迟**轮间可差近 2×** ——
同一被测 `f2dad78`、同一 48 条集,`sut.call` 合计 **187.0 s vs 96.7 s**,逐 case 配对比值**中位数 0.46**(系统性,非离群)。

**已排除的解释**:① 模型网关波动(同期 `judge.grade` **同网关同模型**,p50 三轮稳定在 1583/1637/1630 ms);
② 语料更多导致更慢(慢的那轮是 **70 篇**,比对照轮**更少**)。**原因未查明**。

⇒ 任何基于单点/少数轮的墙钟阈值都会**误报**。把它接成阻断项,等于建一个**假门** —— 而假门比没有门更危险
(它会让人以为有保护)。

## 3. 备选方案

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A 不接线,仅记录** | 维持现状,L1 只作观测 | 零成本、不误报 | **2.2 的问题不解决** —— 越线仍无声 |
| **B 按 48 条线性重定标 + 接线** | 180×48/40 ≈ 216 s 等 | 口径与用例数对齐 | 实测已 **269.2 s** ⇒ **仍会误报**;且等于"单点标定"换"单点标定",没解决方差 |
| **C 分层处置** | **稳定量**接线(**错误率**〔澄清后〕+ **埋点开销占比**);**波动量**(墙钟、`sut` 延迟)只记录并标注"需 ≥N 轮" | 只对有判别力的量设门;避免用不稳的量设阈值 | 墙钟类退化**仍无人自动拦** |
| **D 先补 N 轮分布再定**(M2 类) | 跑重复测量(T4)再标定 | 阈值有统计依据 | **须报备 ~95 万 token**;且按 §2,方差可能仍大 ⇒ 可能标定完仍不能接线 |
| **E 改口径:只对"我方可控量"设 L1 门** | 区别「门自身」与「被测/外部支配」:门只对**自己**负责 | 门对自己的开销/错误负责,职责清晰 | 被测变慢无人拦 —— 但那**本就该由被测自己的监控负责**,不是评测门的职责 |

## 4. 评估标准与建议

**标准**:① 判别力(能不能真的拦住退化)② 误报率(会不会拦不该拦的)③ 成本 ④ 与门职责是否对齐。

**建议 = C + E 的组合**(**待签核**):

1. **L1 只接线「门自身可控」的两个量**:埋点/编排开销占比(<5%)、**错误率**(口径先按 §2.3 澄清);
2. **墙钟与 `sut.call` 延迟降为观测项**,文档里写明「**需 ≥N 轮**才能判退化」,不设单轮阻断阈值;
3. **`总纲.md` §4 与 `eval/阈值.md:25-30` 的口径同步更新**:把"(40 条)"改为"按轮/按用例数",并把
   越线的旧"实测"值标注为**已过时**(保留历史,不删);
4. **墙钟/延迟若要真接线**,必须先有 N 轮分布 ⇒ 另开 DEC + 报备预算(**不在本次**)。
5. **QPS**:业务方已定夺不做并发压测 ⇒ 在门禁对照里**记为显式豁免**,**不写"已达预期基线"**。

**理由**:本轮实测证明延迟类量**由被测/外部支配且轮间可差 2×**;
拿它当阻断阈值 = 建会误报的假门;而门自身可控的量(开销占比、错误率)既稳又有判别力,才是 L1 该接的。

**为什么不选 B**:B 假设"墙钟随用例数线性、方差小",本轮**同时证伪了两点**。
**为什么不选 D(现在)**:应先定"接哪些量",再谈标定;否则花钱标定一个**不该接线**的量。
**为什么不选 A**:它默认接受了"越线无声"这一缺陷。

### ⚠️ 两处 DEC 未覆盖、实施时才浮现的决定(请复核)

1. **`EVAL_TRACE=0` ⇒ L1 不可测 ⇒ 记阻断项**(堵绕过口)。
   `Tracer(enabled=False)` 全部空转 ⇒ 无 span ⇒ 若静默跳过,L1 门可被关观测绕过。
   本项目已有同类教训:「**不带 tracer = 绕开生产路径**」(`docs/复盘/2026-09-11-P4-1-过程错误.md` E2)。
   区分:`tracer=None`(库/单测用法)不算绕开,L1 不适用、不加阻断项。
2. **埋点开销占比加「测量地板」100 ms**(低于地板只报不判)。
   起因:接线后 **8 个既有测试变红** —— 离线桩轮 `root_ms≈1.4 ms`,占比算出 **0.42**;
   而阈值是 5%。根因:该量在极短轮次里由**测量噪声**支配(真实轮 `root≈171,000 ms` ⇒ 占比 ≈0),
   **不具判别力**。按 §5.5 的同一原则(「宁可少接一个,不接一个会误报的」)给地板。
   ⇒ 若你认为"离线轮次也该被拦",说一声即可去掉地板。

**实施中被既有测试抓到的两个真 bug(已修)**:

1. `overhead_ratio` 第一版照抄 `bench.attribute_spans` 的「`spans[0]` 是根」约定 ——
   但**真实 CLI 轮次里第一个 span 是 `evalset.load`**,`run.evaluate` 在后面 ⇒
   把 0.2 ms 的 `evalset.load` 当整轮 ⇒ 占比 1.0 ⇒ 误报阻断。**改为按名字找根**。
2. 我自己写的第一版 L1 测试有两个断言错误(在 `with` 块内设 `duration_ms` 被上下文管理器覆写;
   干净场景的期望值算错)—— 均由**先跑失败**发现。

**守未决项的守卫已按规矩更新**:`tests/test_calibration.py::test_judge_agreement_does_not_block_yet`
里那条「键集合 = 已知三键」的断言**如期变红**。它的用意是「**新增阈值键必须先有 DEC**」,
本次的 DEC 就是本文 ⇒ 把两个 L1 键加进白名单并写明理由,**未削弱守卫**。
