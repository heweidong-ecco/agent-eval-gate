- 日期:2026-09-12 · 状态:**✅ M1 完成**(真值已测得并落进 `eval/阈值.json`);⚠️ **是否作为阻断项 = 未决**(见 §5)

## 0. 结果(2026-09-12,首测)

业务方在 16 条参照集上**盲标**后,用当前判分器逐条重判(`eval-gate calibrate`,16 次调用 / **13,722 token**):

| 指标 | 值 |
|---|---|
| **`judge_human_agreement`** | **0.80**(一致 12 / 已标注 15) |
| **副指标(剔 flag 后)** | **1.00** —— 判分器的 **pass/fail 判定与人的判定 100% 一致** |
| 分歧 | **3 条,全部是 `flag`**,且**全是"半拒答"**(`id=15` / `id=27` / `id=42旧`) |
| 剔除 | 1 条(`id=26`,业务方裁定**用例本身有问题**) |

### 这个数怎么读(关键)

**判分器的毛病不是"判错",是"该定的不定"。** 三条分歧全都是:
被测答「无法回答…但句中出现了候选词」⇒ 判分器给 `flag`(存疑交人),而人的口径是 **pass**。

- 这是**偏安全的一侧**:它不静默放过,而是**把决定推给人**;
- 但它**确实有成本**:每条 flag 都要人看一遍(契约里 flag ⇒ exit 2);
- 而且它**可被定位**:不是散乱的噪声,而是**一个可命名的模式** —— 这正是校准要产出的东西。

### 口径裁定(业务方 2026-09-12)

**「满足」= 字面含其一即符** —— 与用例期望的写法一致:句中出现了候选词即算满足,
**即使整句是拒答 / 答非所问**。(若改用"命中还须切题",那是**改判据口径本身**、会连带影响门的标定,须另写 DEC。)

据此 `id=15` 由「不满足」**改判为「满足」**,三条半拒答口径统一。

## 0.2 过程错误(我方,已落 `docs/复盘/`)

## 1. 为什么做(以及此前为什么一直没做)

在此之前,**门的结论没有外部锚**:判分器判得准不准、判严了没有,全靠门自己"觉得"。
`eval/阈值.json` 里 `judge_human_agreement` 一直挂在 `_doc_only`(未接线、无实测值)。

此前卡住的不是技术,是**人工投入**:`T1b` 记「业务方决定近期不投入人工标注」⇒ 无参照物,接线也空转。
**业务方 2026-09-12 选定 M1 ⇒ 该前提解除**,本 DEC 落地"最小标注"路线(10–20 条,不做全量)。

## 2. 度量口径(三条,都是刻意的)

| # | 口径 | 理由 |
|---|---|---|
| 1 | **只统计真被标注的条目**;未标注与「说不清」**剔除并单独报数** | 「说不清」是**允许的诚实答案**:算成"不一致"等于**惩罚诚实**,人会开始瞎猜;算成"一致"又给指标灌水。**剔除 + 报数**才诚实(报数才知道覆盖够不够) |
| 2 | `judge_human_agreement` = **"judge 判 pass" ↔ "人工判满足"** | 与大白话一致:两者都指向"这条该不该通过" |
| 3 | **flag 单独计**;主指标里 flag 按 **非 pass** 计,另给副指标 `agreement_excl_flag` | flag 既非判对也非判错,而是"判分器自己也没定" —— 它不让该条通过,**人还得看一遍**,这就是它的成本。副指标用来单独看"纯 pass/fail 判得准不准" |

> ⚠️ **被明确排除的做法**:把「说不清」当一致或不一致(见 #1);把 flag 同时算进"判对"和"判错"(会互相抵消,两类问题都看不见)。
> 另:**一条都没标时一致率是 `None` 而不是 `0.0`** —— `0.0` 会被读成"判分器全错"。

## 3. 样本怎么选(这一节是本 DEC 最重要的部分)

**关键约束:样本里必须有"判分器可能错"的条目,这个数才有信息量。**

第一版设想是从最近一轮(48/48 全绿)**抽样** —— 那一池 **45 条全 pass、且全是"软层命中"**:
从中抽样,一致率必然是 1.0 —— **判分器"一律判过"也能拿满分**。⇒ **已否**。

**实际做法:从历史轮次的真实产物里挑,覆盖"判过 / 判错 / 该判未判"三类**:

| 分组 | 条数 | 取材 |
|---|---|---|
| **A 真实失败** | 8 | 被测答错/拒答、当时被判 fail 的真实答案(含 `20260911-224254` 那轮被测生产缺陷期的拒答) |
| **B 争议项** | 2 | 半拒答(旧 `id=42`、`id=27` —— 判分器曾判 flag 的那类) |
| **C 对照(清晰)** | 6 | 最近一轮的直答/跨文档/方向性/must_refuse,用于检验"判分器会不会把好的判坏" |

**最值钱的两条**:`id=19` 的两次观测 —— 答案「带上当前用户的 **ID** 进行过滤」**明显正确**,
却因期望候选只有「用户的 id」(小写形态)而被确定性层判 fail。
⇒ 这类条目正是"判分器/判据可能错"的证据所在;全是 pass 的样本永远看不见它。

**语料依据**:边界条目附了**语料原文**(`documents` 只读查得),否则标注人无法判断
"该答没答"还是"语料本来就没有"(零 token)。

## 5. ✅ 已定:一致率**不作为阻断项**(业务方 2026-09-12 同意)

**决定**:保持"标定值 + 告警",**不接进任何自动门**;另提供 `calibrate --fail-on-below` 开关,
**要不要拦、什么时候拦,由使用方显式指定**(默认关闭)。

四条理由:

1. **样本太薄,不够拦门**:15 条得 1.00,95% 置信下界约 **0.78** —— "1.00"与"0.80"在统计上**还分不开**。
   拿一个分不开真假的数拦发布 = 拿门禁做装饰。
2. **会拦错对象**:一致率反映的是**门自己**跟人齐不齐。它掉下去时该整改的是**判分器/prompt/用例**,
   不是被测 ⇒ 设成阻断 = **被测的发布被门自身的漂移拖住**,方向反了。
3. **成本位置不对**:它要跑 `calibrate`(≈1.4 万 token/次),放进每次 PR 的 CI = 每个 PR 烧 1.4 万 token
   去测一件"每周才需要知道一次"的事。
4. **该拦的东西已有闸**:`l2_task_completion` / `redteam_zero` 拦**被测质量**;一致率是**门的健康度**,
   两者不该共用一个出口。

**落地形态**:

- 现在 = **P2 告警**(与 `flag` 同级):低于 min 就出声 + **点名分歧条目**;
- **指定复测时机**:改 judge 模型 / 改 judge prompt / 改判据分层 ⇒ **必跑**
  (本次修 prompt 正是这么发现的:0.80 → 1.00、flag 3 → 0);
- **升级为阻断的前置条件**(写死,免得日后随手改):① 参照集 **≥30 条**;
  ② 含「堆砌/否定式」与「方向性」两类;③ 复测进**定时任务**(周/月),**不进 PR 门**。
