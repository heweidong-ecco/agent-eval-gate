# 决策记录:DEC-001 · 首发被测样例形态 = 迷你 RAG-QA

- 日期:2026-09-09
- 状态:已采纳
- 关联:阶段1-步骤2 · 产出:`需求基线.md` §6(用例)/§9(范围);影响阶段2 首个样本标定(北极星/阈值)。

## 决策事项
一句话:首发"自带迷你被测样例"选哪种形态——用它验证 agent-eval-gate 工具本身(不自带无法自证),并成为阶段2 定北极星与阈值的数据源。

## 背景与约束
- 已拍板"自用先行 + 自带迷你被测"(业务方 2026-09-09):评测门首先服务作者自己所有 Agent 项目;工具必须先用一个自包含样例自证成立。
- 约束:阶段1→阶段4 首个 MVP 微循环要快;评估集要能体现 judge 的忠实度/检索引擎能力;工程依赖最少;后续真实被测(工具调用类)再横向补覆盖。
- B 依据:评估方法论在 B `05-模块-评估与测试`(忠实度/召回为 RAG 类核心度量),RAG-QA 是唯一既有成熟 judge 口径又有检索引擎可量的形态。

## 备选方案(≥2)
| 方案 | 一句话思路 | 优点 | 缺点 |
|---|---|---|---|
| A · 迷你 RAG-QA | 自带一个迷你问答 Agent(检索少量文档→生成回答),评测问"答得准不准/忠不忠实" | 评估集好造;忠实度/命中度量成熟;依赖最少;首个闭环最快 | 不覆盖工具调用/多步编排,需后续补 |
| B · 迷你工具调用 Agent | 自带一个带 2–3 个工具的 Agent,评测工具调用序列与最终结果 | 更能验证工具准确率/多步 | 依赖被测运行时录制;评估与断言复杂;阶段1 慢 |
| C · 两者都要 | RAG-QA + 工具调用双被测 | 一次验证 judge 泛化 | 阶段1 工作量×1.5,违背 MVP 最速闭环 |

## 评估标准
开发速度 / 依赖与可维护 / 评估集友好度 / 度量成熟度(judge 口径现成)/ 对后续真实被测的迁移价值 / 单人可运维。

## 方案对比
- **A** 开发速度最快,评估集为文本 QA 无需录制,忠实度口径成熟(B 05-评估),是 Kit 方法论的天然首发载体;**缺陷**是不覆盖工具/多步——但工具类评测可由后续真实被测项目补充,非首发阻塞。
- **B** 更贴近"Agent 行为评测"卖点,但自带被测需自建迷你运行时与录制,首轮返工风险高(Walk-through 亦暴露工具类依赖录制,见 `需求基线.md` §8-W3)。
- **C** 违背"先跑通一个闭环再横向扩展"(MVP 纪律),排除。

## 最终决策 + 理由
**选 A(迷你 RAG-QA)。** 理由:首个 MVP 的价值是**验证评测门本身能拦劣化、judge 口径可信**,而非证明能测所有 Agent 形态;RAG-QA 使"忠实度/命中 + judge 一致率"全部可度量、评估集自造无 PII、无外部运行时依赖。工具调用/多步评测作为 DEC-001 的已知减项,交由阶段2 首个真实被测项目(作者自己的工具类 Agent 项目)补覆盖。
> 引用 B `05-模块-评估与测试`:评估是引擎、质量模型自己定——先在一个窄而可信的形态上立住质量模型,再横向扩。

## 影响与后续行动
- `需求基线.md` §6:首发被测落定迷你 RAG-QA;U1(自证闭环)+ U2(真实接入)的评测集与成功标准以此铺开。
- 阶段2:用迷你 RAG-QA 首个样本标定北极星/阈值;设计评测集 schema 时预留工具类字段(不阻塞 RAG-QA)。

## 反悔成本
若日后证明 RAG-QA 单形态不足以说服真实用户(工具类团队),反悔 = 追加迷你工具调用被测(补评估集 + 录制/回放适配,估 v1.1 量级),而非推翻现有评测内核——评测管线(确定性→judge→报告)与被测形态解耦,换被测即换适配器。
