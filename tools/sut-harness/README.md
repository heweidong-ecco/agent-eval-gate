# tools/sut-harness/ · 真实被测的运行适配层

> **一句话**:把外部被测(`01.FastAPI RAG Agent`)**零改动**地跑起来,供评测门做真实链路评测。

## 为什么它在本仓(而不是被测仓)

| 理由 | 说明 |
|---|---|
| **职责归属** | 它是**评测门**为"在受控环境里跑外部被测"造的适配层,属门的基础设施 —— 与 `tools/bench.py`、`tools/ab_regression.py` 同类 |
| **避免第三套运行方式** | 被测仓**已有**自己的官方方式(`docker-compose.yml` / `Dockerfile` / `deploy.sh` / `dev.sh`)。再塞一套进去 = 制造"哪个才是对的"歧义 |
| **不污染对方仓库** | 不往被测的 GitHub 历史里混入评测门的关注点 |
| **随门演进** | 它会随评测门变化(将来要加录制/mock),放本仓才不用每次去改被测仓 |

被测路径通过 `EVAL_SUT_REPO` 注入 ⇒ **本仓不硬编码任何外部绝对路径**。

## ⚠️ 定位:过渡 / 兜底 —— 有退出条件

**触发它的原因**:被测的 `rag-api` 容器**镜像构建于 2026-07-01**,早于 2026-09-10 的模型迁移,
镜像内代码与仓库不一致 → 跑起来会回落到 DashScope(且其 chat 额度已耗尽)。

**它为什么存在**:绕开陈旧镜像(只读挂载仓库 `api/`,跑**当前代码**)+ 补齐镜像缺的运行期依赖。

**退出条件(达到即应退役本目录)**:
- 被测侧用**官方方式**重建镜像可用:`docker compose build api && docker compose up -d api`,且
- 重建后的镜像**能力探针通过**(见下)。

> 即:能走官方路径就走官方路径。本层只是"官方路径暂时不通"时的保障。

## 用法

```bash
export EVAL_SUT_FASTAPI_API_KEY=<admin key>     # 能力探针要用;跳过它会失去最重要的那道保险
tools/sut-harness/run_sut.sh                    # 默认路径;可用 EVAL_SUT_REPO 覆盖
```

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `EVAL_SUT_REPO` | (内置一个默认路径) | 被测仓根目录 |
| `EVAL_SUT_IMAGE` / `EVAL_SUT_CONTAINER` / `EVAL_SUT_NETWORK` | `my-fixed-name-api` / `rag-api-eval` / `my-fixed-name_app-net` | 容器三要素 |
| `EVAL_SUT_DEPS_VOLUME` | `sut-pydeps` | 补装依赖的**持久卷**(只装一次) |

退出码:`0` 就绪且探针通过 · `1` 起不来 · **`2` 起来了但答不了**。

## 文件

| 文件 | 作用 |
|---|---|
| `run_sut.sh` | 起依赖容器 → 起被测容器 → 等就绪 → **能力探针** |
| `sut_run.py` | 最小启动器:**只挂 RAG 路由**,避开前端/看板等重型可选依赖 |
| `sitecustomize.py` | 兼容层:把 langchain 1.x 移走的 legacy agent API(现于 `langchain_classic`)补回 |

容器内**补装**的三个运行期缺件(镜像里没有,装在持久卷 `/deps`):`python-multipart`、`ddgs`、`langchain-classic`。

## 陷阱清单(踩过的,别再踩)

1. **`docker run --env-file` 不剥离行内 `#` 注释** —— 被测 `.env` 里
   `LLM_MODEL_FAST=deepseek-v4-flash   # 轻量角色:…` 会把注释整段当成**值**,
   模型名被污染后网关返回 400。⇒ 必须用 `-e` 显式覆盖(脚本已做)。
2. **`/health` 200 ≠ 被测答得了** —— `/health` 只查 DB/Redis。**能力探针是必需的**:
   2026-09-11 实测,被测能通过健康检查却对真实问题一律回「无法回答」(根因是被测的查询改写
   因 `max_tokens` 被推理吃满而返回空)。**跳过探针,跑完的结果会被误读成"被测质量崩了"。**
3. **最小启动器与生产形态不同** —— 只挂 RAG 路由 ⇒ 中间件/缓存等未加载。
   **评测结论的"可比性"要连同这一点一起说明**(见 `docs/reports/P4-1/端到端测试报告.md` §3.6)。
4. **别直接用原 `rag-api` 容器** —— 镜像陈旧,跑的是 07-01 的代码。
5. **`docker logs` 为空 ≠ 进程崩了**(2026-09-12 实测) —— 容器 Cmd 的第一步是
   `pip install --quiet --target=/deps python-multipart ddgs langchain-classic`(输出被 `| tail -1` 吞掉),
   紧接着才起 uvicorn。所以**刚重建的头几十秒**:容器 `Up`、`docker logs` **完全空白**、
   `/health` 连不上 —— 这三条同时出现**看着就像崩了**,实际只是 pip 还在跑。
   ⇒ **判据是 `/health` + 能力探针,不是日志有没有输出**;`run_sut.sh` 报「服务未就绪」时,
   先**等 30–60 秒再判**,别急着重启(重启会让 pip 从头再来)。
   > 另有两条环境教训(与本节同源):容器内**没有 `ps`**(`docker exec … ps` 必失败,别拿它当判据);
   > `docker inspect` 的 `.Config.Cmd` 能一眼看出容器当前处于哪个阶段。
